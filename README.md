# RTK Bridge — UM981 ⇄ Android (ESP32-WROOM-32)

สะพานข้อมูลระหว่างบอร์ด **UM981** กับ **จอ Android** ผ่าน ESP32-WROOM-32 (38 pin, CP2102)
เขียนขึ้นเพื่อแก้ปัญหาเฉพาะข้อเดียว: **แอปค้าง/หลุด แล้วต่อกลับไม่ได้จนกว่าจะถอดไฟบอร์ด**

---

## ปัญหาเดิมเกิดจากอะไร

เมื่อแอปฝั่งจอค้างหรือถูก OS kill มันมัก **ไม่ได้ปิด socket อย่างสุภาพ** ฝั่งบอร์ดจึงไม่เคย
รู้ว่าปลายทางตายแล้ว แล้วเกิดลูกโซ่นี้ขึ้น:

```
แอปตาย → ไม่มีใครอ่านข้อมูล → บัฟเฟอร์ฝั่งส่งเต็มใน 1-2 วินาที
        → SerialBT.write() บล็อกค้าง → ลูปหลักหยุดเดิน
        → ไม่มีใครดูด UART → RX FIFO ล้น
        → บอร์ดค้างทั้งตัว + slot เดียวที่มีถูกศพจองไว้
        → เครื่องใหม่ต่อไม่ได้ ต้องถอดไฟ
```

ต่อให้เขียน retry ฝั่งแอปดีแค่ไหนก็ไม่ช่วย เพราะบอร์ดตายไปก่อนแล้ว

เสริมอีกข้อ: `BluetoothSerial.h` ของ Arduino ห่อ SPP ไว้ **session เดียวแบบฮาร์ดโค้ด**
เลยไม่มีทางรองรับหลายเครื่องเลย เฟิร์มแวร์นี้จึงเรียก `esp_spp_api` ของ ESP-IDF ตรงๆ แทน

---

## หลักการออกแบบ 3 ข้อ

1. **ห้ามมีอะไรบนเส้นทางข้อมูลบล็อก** — ปลายทางช้า ให้ทิ้งข้อมูล**เก่า** ไม่ใช่หยุดรอ
   ค่าพิกัดเมื่อ 2 วินาทีที่แล้วไม่มีค่าอยู่แล้ว การทิ้งมันดีกว่าดันแรงดันย้อนกลับไปทำ UART ล้น
2. **ปลายทางที่หยุดรับ = ตาย** ตัดทิ้งภายใน 6 วินาที ไม่รอ link supervision timeout
   ของ Bluetooth ที่กินเวลา 20-32 วินาที หรือไม่มาเลย
3. **Newest wins** — เครื่องใหม่ที่มาเคาะประตูได้เข้าเสมอ ถ้าเต็มก็เตะตัวที่นิ่งที่สุดออก

## สิ่งที่ได้เพิ่มมา

| กลไก | ทำอะไร | ตั้งค่าที่ |
|---|---|---|
| คิวต่อ client แบบ drop-oldest | ทิ้งเป็น**ทั้งบรรทัด** แอปไม่มีวันเจอ sentence ขาดกลาง | `CLIENT_RING_SIZE` |
| ตัวจับ stall | client ไม่ยอมรับข้อมูลเกิน 6 วิ → ตัดทิ้ง คืน slot | `STALL_TIMEOUT_MS` |
| ยึด slot คืนเอง | ถ้า close event ไม่เคยมา ยึด slot คืนเองใน 3 วิ | `KICK_GRACE_MS` |
| ประกาศตัวซ้ำ | ตั้ง scan mode ใหม่ทุกครั้งที่มีเครื่องเข้า/ออก กัน BT stack แอบเลิก discoverable | — |
| SPP หลาย session | เรียก `esp_spp_api` ตรง แทน `BluetoothSerial` | `SPP_MAX_CLIENTS` |
| WiFi TCP server | เส้นทางที่รองรับหลายเครื่องได้จริง + TCP keepalive จับ socket ตายใน ~11 วิ | `TCP_MAX_CLIENTS` |
| อนุญาโตตุลาการ uplink | มีแค่เครื่องเดียวที่ป้อน RTCM ได้ กัน NTRIP สองสายตีกันจนเฟรมพัง | `UPLINK_OWNER_TIMEOUT_MS` |
| RX buffer 8 KB | ของเดิม 256 ไบต์ เต็มใน ~11 ms ที่ 230400 | `GNSS_RX_BUFFER` |
| Task watchdog + wedge reboot | ถ้า BT stack ค้างจริงๆ รีบูตดีกว่านอนตายคาสนาม | `BT_WEDGE_REBOOT_MS` |

## การต่อสาย

| ESP32 (38 pin) | UM981 | หมายเหตุ |
|---|---|---|
| GPIO16 (RX2) | TX | |
| GPIO17 (TX2) | RX | |
| GND | GND | **ต้องต่อร่วมกัน** |
| 3V3 / 5V | VCC | ดู logic level ของบอร์ด UM981 ที่ใช้ |

**TX/RX ต้องไขว้** ต่อตรงข้างต่อข้างจะเงียบสนิทหาสาเหตุไม่เจอ

GPIO16/17 ใช้ได้เพราะเป็น **WROOM-32** (ไม่มี PSRAM)
ถ้าเปลี่ยนไปใช้ **WROVER** ต้องย้ายขา เพราะ 16/17 ถูก PSRAM จองไว้

UART ของ ESP32 รับได้ **3.3V เท่านั้น** ถ้าบอร์ด UM981 จ่ายไฟ 5V แล้ว UART ออกมา 5V ด้วย
GPIO16 พังได้ ยืนยันก่อนต่อ

### งบกระแสไฟ — อ่านก่อนโทษเฟิร์มแวร์

ถ้าจ่ายไฟ UM981 จาก pin 5V ของ ESP32 ขณะที่ ESP32 กินไฟจาก USB ทั้งระบบจะแขวนอยู่บน
พอร์ต USB เส้นเดียว:

| ตัวกิน | กระแส |
|---|---|
| ESP32, Bluetooth อย่างเดียว (**ค่า default**) | ~30-50 mA |
| ESP32, ถ้าเปิด WiFi AP ด้วย | +80-120 mA พีคตอน TX แตะ ~500 mA |
| UM981 (multi-band RTK) | ~100-200 mA |
| เสาอากาศ active (LNA) | ~20-50 mA |

USB 2.0 จ่ายได้ 500 mA เฟิร์มแวร์นี้จึง **ปิด WiFi มาตั้งแต่ต้น** (`ENABLE_WIFI_BRIDGE 0`)
เพราะ AP mode ยิง beacon ทุก 100 ms ตลอดเวลาไม่ว่าจะมีใครต่อหรือไม่ กินมากกว่าตัว
Bluetooth เองเสียอีก ขณะที่ข้อมูลจริงแค่ 3-5 kB/s ซึ่ง SPP เหลือเฟือ

ถ้าเปิด WiFi แล้วไฟไม่พอ จะเจอ brownout reset สุ่มๆ ซึ่งหน้าตาเหมือนอาการ "หลุดเอง"
ที่เฟิร์มแวร์นี้แก้อยู่พอดี ทำให้ไล่บั๊กผิดตัว

แยกให้ขาดจาก serial console:

| เห็นอะไร | แปลว่า |
|---|---|
| `Brownout detector was triggered` | ไฟไม่พอ ไม่ใช่บั๊ก |
| `RTK Bridge starting` โผล่ซ้ำเรื่อยๆ | บอร์ดรีบูตวน ก็คือไฟ |
| `stalled ... - dropping it` แล้วต่อกลับได้ | เฟิร์มแวร์ทำงานถูกต้อง |

ตอนเทสต์ให้ใช้ USB 3.0 (900 mA) หรือ powered hub ถ้ายังไม่พอให้แยกไฟ UM981 ต่างหาก
แล้วต่อ GND ร่วมกัน

### แฟลชโดยไม่ต้องถอด UM981

bootloader ใช้ GPIO1/3 (TX0/RX0) ผ่าน CP2102 คนละคู่กับ GPIO16/17 ที่ต่อ UM981
เสียบคาไว้ได้ตลอด แก้โค้ด แฟลช และ monitor พร้อมกันได้

## การเชื่อมต่อจากจอ Android

**ทาง Bluetooth** — จับคู่กับ `RTK-Bridge` แล้วต่อ SPP เหมือนเดิม โค้ดฝั่งแอปไม่ต้องแก้

**ทาง WiFi — ปิดอยู่ตาม default** ถ้าต้องการให้ตั้ง `ENABLE_WIFI_BRIDGE 1` ใน `config.h`
แล้วแฟลชใหม่ จะได้:

```
SSID : RTK-Bridge
Pass : rtk123456
IP   : 192.168.4.1
Port : 2947
```

เปิดเมื่อจำเป็นจริงๆ เท่านั้น เพราะแลกมาด้วยไฟ ~80-120 mA

## โครงสร้างโปรเจกต์

`RTKBridge/` เป็น sketch folder ของ Arduino IDE และ `platformio.ini` ก็ชี้มาที่โฟลเดอร์เดียวกัน
**ซอร์สมีชุดเดียว** เปิดด้วย toolchain ไหนก็ได้ ไม่ต้องคอยซิงก์สองชุด

## Build — Arduino IDE

เปิด `RTKBridge/RTKBridge.ino` แล้วตั้งค่าตามนี้:

| หัวข้อ | ค่า | เหตุผล |
|---|---|---|
| Board | ESP32 Dev Module | |
| **Partition Scheme** | **Minimal SPIFFS (1.9MB APP)** | เผื่อไว้ พอเปิด WiFi แล้ว partition default ใส่ไม่ลง |
| **Core Debug Level** | **Info** | ถ้าต่ำกว่านี้จะไม่เห็นบรรทัด connect / stall / drop |
| Upload Speed | 921600 | |

## Build — บรรทัดคำสั่ง

```bash
tools/flash-and-watch.sh /dev/ttyUSB0 30     # arduino-cli: compile + flash + ดู serial
pio run -t upload && pio device monitor      # หรือทาง platformio
```

log จะพิมพ์ทุก 5 วินาที บอกจำนวน client, ไบต์ที่ส่ง/ทิ้ง, คิวค้าง และ heap

## วิธีทดสอบว่าหายจริง

จำลองอาการเดิมให้ตรงๆ:

1. ต่อแอปเข้าบอร์ด ดูให้ข้อมูลไหล
2. **Force stop** แอปจาก Settings (อย่ากดปิดปกติ — ต้องให้มันตายแบบไม่ปิด socket)
3. ดู serial monitor จะขึ้น `stalled for ... - dropping it` ภายใน ~6 วินาที
4. เปิดแอปต่อกลับ — ต้องติดทันที ไม่ต้องแตะบอร์ด

**สำคัญ: ต้อง Force stop เท่านั้น** ถ้ากดปิดแอปตามปกติ Android จะปิด socket ให้เรียบร้อย
ซึ่งไม่ใช่อาการที่เรากำลังแก้ ถ้ามี adb สั่งจากคอมได้เลย:

```bash
adb shell am force-stop <package-name>
```

ทดสอบ multi-device: ต่อเครื่องที่สอง (และสาม) พร้อมกัน ดูบรรทัด `clients spp=N tcp=M`

## ข้อควรรู้ / ข้อจำกัดที่ยังเหลือ

- **เพดาน Bluetooth คือ 2 เครื่อง และเราขยับไม่ได้** ตรวจจาก sdkconfig ที่
  arduino-esp32 แจกมาจริง (เช็กทั้ง 2.0.17 และ libs ของ 3.x บน IDF 5.1 ตรงกัน):
  `CONFIG_BTDM_CTRL_BR_EDR_MAX_ACL_CONN=2` ← ตัวที่บีบจริง ส่วน
  `CONFIG_BT_ACL_CONNECTIONS=4` ฝั่ง host ไม่มีวันไปถึง
- **ตัวคุมคือ controller ไม่ใช่ host** เครื่องที่ 3 ถูกปฏิเสธต่ำกว่าชั้น host
  เฟิร์มแวร์**ไม่ได้รับ event และไม่มี log** จึงเตะใครออกแทนให้ไม่ได้
  จะขยับเพดานต้อง rebuild ตัว controller library ซึ่งทำจาก Arduino ไม่ได้
- ด้วยจอเดียว `SPP_MAX_CLIENTS 2` ให้ผลดีที่สุด: slot ที่สองว่างเสมอ แอปที่แครช
  **ต่อกลับเข้าได้ทันที** ไม่ต้องรอ reaper เก็บศพที่ค้างอยู่ slot แรกด้วยซ้ำ
- ถ้าโทรศัพท์เดินออกนอกระยะหรือปิด Bluetooth เลย จะยังต้องรอ supervision timeout
  ของตัว controller (~20 วิ) ซึ่งอยู่นอกเหนือการควบคุมของเฟิร์มแวร์ แต่ตัวจับ stall
  จะสั่งตัดที่ 6 วิและยึด slot คืนที่ 9 วิอยู่ดี
- ถ้าตั้ง UM981 ให้ส่ง **ข้อมูลไบนารี** ลงมาด้วย ต้องตั้ง `LINE_FRAMED_DOWNLINK 0`
  ไม่งั้นการตัดตามบรรทัดจะตีความผิด
- **WiFi ปิดตาม default** ผลคือจำนวนเครื่องที่ต่อพร้อมกันได้ขึ้นกับเพดานของ Bluedroid
  ล้วนๆ ถ้าวันหนึ่งต้องการเกินนั้นให้เปิด `ENABLE_WIFI_BRIDGE 1` (แลกกับไฟ ~80-120 mA)
  เปิดพร้อม Bluetooth ได้ ตัว coexistence ของ ESP32 รับไหวสบายที่ ~5 kB/s
- ถ้าไฟยังตึงอยู่ ลดได้อีก 20-30 mA ด้วย `CPU_FREQ_MHZ 80` — **ห้ามต่ำกว่า 80**
  เพราะเป็นทั้งขั้นต่ำของ Bluetooth และจุดที่ APB clock ยังเลี้ยง baud rate ได้ถูกต้อง
- `ByteRing` ผ่าน unit test บนเครื่อง host แล้ว (ASan/UBSan) แต่**ตัวเฟิร์มแวร์เต็มยัง
  ไม่ได้คอมไพล์** เพราะ environment ที่เขียนเข้าถึง PlatformIO registry ไม่ได้
  กรุณา `pio run` ยืนยันก่อนแฟลชจริง
