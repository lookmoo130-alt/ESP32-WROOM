# RTK Bridge — UM981 ⇄ Android (ESP32-WROOM-32)

สะพานข้อมูลระหว่างบอร์ด **UM981** กับ **จอ Android** ผ่าน ESP32-WROOM-32 (38 pin, CP2102)
เขียนขึ้นเพื่อแก้ปัญหาเฉพาะข้อเดียว: **แอปค้าง/หลุด แล้วต่อกลับไม่ได้จนกว่าจะถอดไฟบอร์ด**

---

## ปัญหาเดิมเกิดจากอะไร

เมื่อแอปฝั่งจอค้างหรือถูก OS kill มันมัก **ไม่ได้ปิด socket อย่างสุภาพ** ฝั่งบอร์ดจึงไม่เคย
รู้ว่าปลายทางตายแล้ว แล้วเกิดลูกโซ่นี้ขึ้น:

```
แอปตาย → ไม่มีใครอ่านข้อมูล → บัฟเฟอร์ฝั่งส่งเต็มใน 1-2 วินาที
        → SerialBT.write() บล็อกค้าง → ลูปหลักหยุดเดิน
        → ไม่มีใครดูด UART → RX FIFO ล้น
        → บอร์ดค้างทั้งตัว + slot เดียวที่มีถูกศพจองไว้
        → เครื่องใหม่ต่อไม่ได้ ต้องถอดไฟ
```

ต่อให้เขียน retry ฝั่งแอปดีแค่ไหนก็ไม่ช่วย เพราะบอร์ดตายไปก่อนแล้ว

เสริมอีกข้อ: `BluetoothSerial.h` ของ Arduino ห่อ SPP ไว้ **session เดียวแบบฮาร์ดโค้ด**
เลยไม่มีทางรองรับหลายเครื่องเลย เฟิร์มแวร์นี้จึงเรียก `esp_spp_api` ของ ESP-IDF ตรงๆ แทน

---

## หลักการออกแบบ 3 ข้อ

1. **ห้ามมีอะไรบนเส้นทางข้อมูลบล็อก** — ปลายทางช้า ให้ทิ้งข้อมูล**เก่า** ไม่ใช่หยุดรอ
   ค่าพิกัดเมื่อ 2 วินาทีที่แล้วไม่มีค่าอยู่แล้ว การทิ้งมันดีกว่าดันแรงดันย้อนกลับไปทำ UART ล้น
2. **ปลายทางที่หยุดรับ = ตาย** ตัดทิ้งภายใน 6 วินาที ไม่รอ link supervision timeout
   ของ Bluetooth ที่กินเวลา 20-32 วินาที หรือไม่มาเลย
3. **Newest wins** — เครื่องใหม่ที่มาเคาะประตูได้เข้าเสมอ ถ้าเต็มก็เตะตัวที่นิ่งที่สุดออก

## สิ่งที่ได้เพิ่มมา

| กลไก | ทำอะไร | ตั้งค่าที่ |
|---|---|---|
| คิวต่อ client แบบ drop-oldest | ทิ้งเป็น**ทั้งบรรทัด** แอปไม่มีวันเจอ sentence ขาดกลาง | `CLIENT_RING_SIZE` |
| ตัวจับ stall | client ไม่ยอมรับข้อมูลเกิน 6 วิ → ตัดทิ้ง คืน slot | `STALL_TIMEOUT_MS` |
| ยึด slot คืนเอง | ถ้า close event ไม่เคยมา ยึด slot คืนเองใน 3 วิ | `KICK_GRACE_MS` |
| ประกาศตัวซ้ำ | ตั้ง scan mode ใหม่ทุกครั้งที่มีเครื่องเข้า/ออก กัน BT stack แอบเลิก discoverable | — |
| SPP หลาย session | เรียก `esp_spp_api` ตรง แทน `BluetoothSerial` | `SPP_MAX_CLIENTS` |
| WiFi TCP server | เส้นทางที่รองรับหลายเครื่องได้จริง + TCP keepalive จับ socket ตายใน ~11 วิ | `TCP_MAX_CLIENTS` |
| อนุญาโตตุลาการ uplink | มีแค่เครื่องเดียวที่ป้อน RTCM ได้ กัน NTRIP สองสายตีกันจนเฟรมพัง | `UPLINK_OWNER_TIMEOUT_MS` |
| RX buffer 8 KB | ของเดิม 256 ไบต์ เต็มใน ~11 ms ที่ 230400 | `GNSS_RX_BUFFER` |
| Task watchdog + wedge reboot | ถ้า BT stack ค้างจริงๆ รีบูตดีกว่านอนตายคาสนาม | `BT_WEDGE_REBOOT_MS` |

## การต่อสาย

| ESP32 (38 pin) | UM981 | หมายเหตุ |
|---|---|---|
| GPIO16 (RX2) | TX | |
| GPIO17 (TX2) | RX | |
| GND | GND | **ต้องต่อร่วมกัน** |
| 3V3 / 5V | VCC | ดู logic level ของบอร์ด UM981 ที่ใช้ |

GPIO16/17 ใช้ได้เพราะเป็น **WROOM-32** (ไม่มี PSRAM)
ถ้าเปลี่ยนไปใช้ **WROVER** ต้องย้ายขา เพราะ 16/17 ถูก PSRAM จองไว้

## วิธีทดสอบว่าหายจริง

จำลองอาการเดิมให้ตรงๆ:

1. ต่อแอปเข้าบอร์ด ดูให้ข้อมูลไหล
2. **Force stop** แอปจาก Settings (อย่ากดปิดปกติ — ต้องให้มันตายแบบไม่ปิด socket)
3. ดู serial monitor จะขึ้น `stalled for ... - dropping it` ภายใน ~6 วินาที
4. เปิดแอปต่อกลับ — ต้องติดทันที ไม่ต้องแตะบอร์ด

ทดสอบ multi-device: ต่อเครื่องที่สอง (และสาม) พร้อมกัน ดูบรรทัด `clients spp=N tcp=M`

## ข้อควรรู้ / ข้อจำกัดที่ยังเหลือ

- **เพดาน session ของ SPP ไม่ได้อยู่ในมือเรา** มันคือค่า `BTA_JV_MAX_RFC_SR_SESSION`
  ที่คอมไพล์มากับ Bluedroid ของ arduino-esp32 (ปกติ 3) โค้ดรับได้เท่าที่ stack ให้
  และถ้าโดนปฏิเสธจะขึ้น `SPP rejected (table full)` ใน log
  **ถ้าต้องการหลายเครื่องแบบชัวร์ ให้ใช้ทาง WiFi TCP**
- ถ้าโทรศัพท์เดินออกนอกระยะหรือปิด Bluetooth เลย จะยังต้องรอ supervision timeout
  ของตัว controller (~20 วิ) ซึ่งอยู่นอกเหนือการควบคุมของเฟิร์มแวร์ แต่ตัวจับ stall
  จะสั่งตัดที่ 6 วิและยึด slot คืนที่ 9 วิอยู่ดี
- ถ้าตั้ง UM981 ให้ส่ง **ข้อมูลไบนารี** ลงมาด้วย ต้องตั้ง `LINE_FRAMED_DOWNLINK 0`
  ไม่งั้นการตัดตามบรรทัดจะตีความผิด
- เปิด WiFi + Bluetooth พร้อมกันใช้ coexistence ของ ESP32 ที่ ~5 kB/s ไม่มีปัญหา
  แต่ถ้าอยากตัดตัวแปรทิ้งให้ตั้ง `ENABLE_WIFI_BRIDGE 0`
- `ByteRing` ผ่าน unit test บนเครื่อง host แล้ว (ASan/UBSan) แต่**ตัวเฟิร์มแวร์เต็มยัง
  ไม่ได้คอมไพล์** เพราะ environment ที่เขียนเข้าถึง PlatformIO registry ไม่ได้
  กรุณา `pio run` ยืนยันก่อนแฟลชจริง
